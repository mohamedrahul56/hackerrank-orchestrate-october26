# Performance report

Generated by `code/evaluation/performance_report.py` from two `code/tools/profile_run.py --runs 3` benchmarks (fresh process per run, median reported). Nothing here is estimated: every number is a measurement on the machine below.

Machine: Linux-6.18.44-fc-v153-x86_64-with-glibc2.39, 4 logical CPUs, Python 3.13.17. The auditor is single-threaded here (no model calls in these runs), so CPU count does not matter; absolute seconds do depend on the machine, the ratios are the finding.

## 1. What was measured

* **x1** is the real input: the 518 requests of `dataset/deletion_requests.csv` (plus the 32 sample requests the auditor always loads).
* **x2 ... x20** repeat every request row K times under new case ids (`case_7__r3`), in a temporary folder where every other dataset file is linked unchanged. x20 is 10,360 requests. The repeated rows are the same people with the same evidence, so they are **not independent cases**: their answers differ from the real run (copies compete for the same free accounts). Only the cost is meaningful, not the statuses.
* *Before* is the code at the start of the profiling work (commit `e34122c`) with only the stage timers added; *after* is the current code. The output file is byte-identical between before and after at every scale (sha256 prefixes in the table), so the indexes changed the cost and nothing else.

## 5. What was quadratic, and what was done about it

Profiling (stage timers, `--cprofile`) found one stage whose cost per request grew with the input: the timeline discovery. The per-case audit, classification, writing and the fixed evidence parsing did not. Discovery took 0.19 s at x1 and 16.95 s at x40 before (91x for 40x the input); after: 0.02 s and 0.78 s (32x). Indexes were built only for the loops that profiling showed:

| where | quadratic because | index | same answers |
|---|---|---|---|
| account candidates (`discover.assign_accounts`) | every case scanned every account's delete events for its time window | events sorted once by time, a bisect per case | output sha256 identical at every scale |
| account elimination and phase resolution | after every acceptance all unresolved cases were re-ranked and every claimant list rebuilt | inverted index account to claimant cases, a heap with lazy invalidation, memoized scores; the multi-pass order of the old loop is reproduced exactly | identical |
| anonymized-analytics candidates | every case scanned every anonymization event, and for each pair `_foreign_chain` scanned every policy action of every user | events sorted by time (bisect), policy actions sorted by time (bisect over the next 25 minutes), result per event memoized | identical |
| analytics elimination and phase | claimant lists rebuilt per case; rivals found by scanning all scored cases | precomputed claimant counts and a resource to cases index | identical |
| cohort snapshot (`case_inputs`) | every case scanned every observation | one pass building file to profile-resources | identical |

**Residual growth, stated plainly.** After the change, discovery grew 32x for 40x the input from x1 to x40 (overall exponent 0.94) and is 8% of the run at x40 (0.78 s of 9.21 s). Its neighbouring-scale exponents in section 4 jump around (between 0.55 and 1.43) because its times are a few hundred milliseconds and runs vary by a few percent: do not read them one by one. Validation shows the same effect at the top scale: its cost per request rises between the last two scales (table above), while the profiler's per-call cost of `validate_case` was flat (about 91 microseconds per call at x20 and 86 at x40 in two `--cprofile` runs, not stored in the benchmark files). That points to memory and garbage-collection pressure rather than an algorithm, but this was not isolated.

Not indexed, on purpose: classification (a regex pass per request, linear: it is the largest remaining stage at the top scale), the per-case audit and validation (linear). No cache was added for repeated request text, because that would only help the artificial repeated-row input, not real data.

## 6. What is NOT scaled - read this before relying on the numbers

This is a **batch auditor, not a service**. It reads one dataset, writes one `output.csv` and exits.

* **Everything is held in memory** in one process: all evidence observations, the whole activity stream, every request. Memory grows linearly with cases (above) and with evidence, and nothing is paged to disk.
* **Single process, single thread.** There is no parallelism over cases; the only concurrency in the code is the bounded pool for reading screenshots (`llm.max_concurrency`) with a vision model (not exercised in these runs).
* **Discovery is global.** Assigning an id-less account or analytics record to a case needs the other cases (elimination), so cases cannot be audited in independent shards, and adding one request can change another case's answer. A service answering one request at a time would need a different design.
* **Only the requests were scaled.** The evidence files (103 files, 4 MB), the activity stream (a few thousand rows) and the identity tables were NOT scaled. Their parsing is a fixed cost here (about 0.29 s); a dataset with 10x the evidence would pay that 10x, and no growth law for it was measured. Quadratic behaviour in the number of evidence files, activity rows or users may exist and was not tested.
* **The repeated rows are not independent data** (same people and evidence). Real 10,000-request data would have more distinct accounts and evidence; the timings show the cost of the algorithms on this shape of data, not a forecast for other data.
* **Model latency and cost are not benchmarked.** These runs used no vision model (no API key was available). Reading screenshots would add one model call per PNG (11 in this dataset) at network latency; the concurrency bound, 429 backoff and cache are tested with a fake client only.
* **No behaviour under failure at scale** (disk full, huge request text, adversarial inputs) was measured beyond the robustness tests.

## 7. Reproduce

```text
python3 code/tools/profile_run.py --repeat 1 2 5 10 20 --runs 3 --save after.json --table
python3 code/evaluation/performance_report.py --before before.json --after after.json
```

`before.json` was produced the same way on a checkout of commit `e34122c` with only the stage timers added (`code/tools/profile_run.py` needs `Auditor.timings`). Absolute seconds vary by machine and by load; run the two benchmarks back to back, as was done here, when comparing.
